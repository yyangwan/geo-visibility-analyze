# E01 行动不可变修订与相关依赖

本轮完成行动计划的后端修订和审批基础。A05 生成的任务包进入同一套 ActionPlan；当前修订号指向 ActionPlanRevision 的确切版本，旧版本只保留历史。没有新增行动系统、数据库字段或迁移，没有修改门户样式、网关或线上环境。

## 客户可以获得的能力与接入状态

- 交付提纲、验收、选定自有事实等变化形成新版本，原批准不适用于新版本。
- 可以明确选择同一逻辑任务在另一个已发布 Run 中的诊断，保留旧 Run 和原批准记录。
- 只核对任务实际依赖的品牌、原文、问题、材料和事实。新增无关事实、无关品牌、业务偏好或较新的 Run 不会自动撤销计划批准。
- 相关依赖发生变化时返回具体的前后值与原因，供页面提示并引导修订重批。

这些能力目前通过后端 API 提供。U02/U03 的任务详情、版本差异和重新审批页面仍待接入；不把接口完成视为客户操作流程已完成。正式内容桥、执行交付、观察效果和独立语义/价值验收分别属于 E02、E03、M01/M02、Q01/Q02。

## 保存与审批

首次创建计划即保存第一份 ActionPlanRevision，内容包括标题、完整诊断/TaskPack、来源 Run、task_key、相关依赖、修改人和原因。ActionPlan.title/target 是当前版本的投影；读取和批准都会校验投影与不可变修订一致。

修订签名覆盖整个任务、所有平台子目标、原问题、诊断证据、自有事实选择、依赖和修订来源。ActionApproval 的 HMAC 绑定修订 ID、编号、载荷和依赖，以及具名审批人、角色、理由。批准范围仍为 investigation_plan，publication_allowed 始终为 false。

新修订状态为 proposed，必须独立批准。旧请求的准确重试可返回原收据，但不会批准当前新版本。已批准版本不能通过覆盖标题、目标或依赖来延续批准。没有实质任务或依赖变化的空修订被拒绝。

## 相关依赖范围

| 依赖 | 核对范围与失效条件 |
|---|---|
| 原始观察 | 来源 Run、其固定输入和已发布状态；修改既有 manifest 会被识别，较新 Run 本身不撤销旧计划 |
| 解释规则 | Run 的分析签名与当前规则/模型签名；解释版本变化需重新分析和明确选择新诊断 |
| 品牌身份 | 本任务目标、比较对象和相关回答中的实体；别名链、出现归属及注册名称冲突也纳入核对，偏好排序不纳入 |
| 问题 | 原问题与本平台的审核、资格、主场景和需求原文；其他问题的修改不改变本任务依赖 |
| 原文证据 | 同项目同 Run 的真实 owner/segment、完整文字 hash、精确 Unicode code point 范围与逐字引文；反向证据同样核对 |
| 引用来源 | 本任务使用的来源、冻结快照版本/完整性、质量和存储指纹及该文档最近取得的快照；同一快照的重复取得不因新收据 ID 而失效，存储键只参与 hash、不向 API 暴露 |
| 人工证据审核 | 本任务相关 ClaimEvidence 的最新审核记录；不绑定全项目的无关审核 |
| 我方事实 | 只核对实际选定 ID 的版本、原文、归属、范围、有效期及来源资格；撤回、过期、换版或撤销材料核实会阻断 |
| 我方材料 | 指定的材料版本、完整性和具名核实；材料换版不自动授权使用新版本 |

任务事实选择只证明该事实当前有效且属于任务自己的品牌，不证明它在语义上足以支持交付中的任何主张。E02 仍须独立做事实资格、适用范围与内容消费校验。缺材料不是缺产品能力。

## 修订方式与权限

`POST /api/intelligence/actions/{id}/revisions` 接受 expectedRevision、idempotencyKey、reason，可附 title、taskPack 或同项目的 diagnosisId。

- expectedRevision 必须是严格整数并等于当前指针；同项目幂等键只接受完全相同的请求与修改人。
- 人工修订可以具体化交付、提纲、验收、渠道及选择有效自有事实。目标品牌、资产身份、事实改动键、执行意图、诊断证据、平台/问题目标、原问题、材料 URL 和审核受众不能伪造或静默截断。
- 需要改变分析范围或加入平台子目标时，显式选取同 task_key 的已发布诊断；不通过客户端自己编造分析结果。新材料资产或不同事实改动属于另一个任务键。
- 原 Run 的相关身份、问题或解释已经改变时，单改标题不能重新签署原解释，必须明确选择合适的新诊断。事实补齐/撤回则可通过明确选择新的事实或移除旧事实形成新修订。
- operational 类型任务可以修订交付标题，不能重新绑定到任意另一条诊断。
- 沿用项目写权限和具名操作人要求；viewer 只读。GET 不创建状态、任务、队列工作或模型调用。

`GET /actions/{id}` 返回当前版本、依赖差异和有效审批状态；`GET /actions/{id}/revisions` 按修订号降序分页，返回原载荷、依赖、修改理由、历史批准签名和绑定的草稿批准编号。创建修订和历史记录均提供 changes_from_previous，分别列出任务字段与相关依赖的前后差异。历史签名正确不代表当前可以执行。

## 并发与重试

写入先按既有材料/配置流程锁项目头，再按审计 ID 排序取锁，然后锁行动当前指针。版本和审批收据使用当前锁定读，避免 MySQL REPEATABLE READ 中等待锁以后仍查不到刚提交的收据。参与审批的当前事实、材料、身份和审核同样使用当前读。两个旧版本修改只能有一个成功；同一请求的并发重试返回同一个不可变修订。

读取项目头不会为 GET 或没有注册配置的 operational 任务创建项目。使用现有预留的 ActionPlanRevision 表和唯一约束，未升级或重建任何数据库。

## 草稿边界

TaskPack v2 仍禁止进入旧 EvidenceBrief v2，避免丢失多平台和原问题。已有 v2 草稿批准在服务端签名载荷中保存私有的行动修订绑定；导出时核对该绑定，旧草稿不会在新计划批准以后恢复有效。私有绑定不改变对外 v2 合同。历史记录可定位原行动修订。

v2 草稿及旧报表/事实批准的全局 stamp 机制本轮保留；E01 的相关依赖替代发生在行动计划及选中事实的校验中。E02 必须完成共享 FactSource、正式 EvidenceBrief v3、跨方签名/能力声明、事实重新核对和发送，才能宣称完整内容链路已升级。

## 验证与边界

- 修订专项涵盖不可变历史、批准重用防护、准确幂等、相关注册身份/同名冲突、无关偏好/身份/新 Run、不实原文、诊断范围伪造、选中事实撤回、问题审核范围、来源快照变化、旧草稿与项目权限。
- 真实 MySQL 验证并发修订单赢家、相同请求准确重试、等待项目锁期间提交的事实撤回，以及原 A05 Pipeline 到具体任务计划的链路。规则与上下文提供者为测试实现，没有真实模型调用。
- 源码离线 API/worker/storage/PDF 入口通过，storage=development_local_only、release_eligible=false。它不等同于新的 Docker 镜像或生产联调。
