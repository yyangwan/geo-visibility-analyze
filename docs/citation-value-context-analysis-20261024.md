# 价值分析 v3：全量信息单元与问题语境

本轮完成 A02 分析内核的本地实现。没有改动页面、采集端、生产服务或历史 Run；独立语义质量验收仍属于 Q01，整个方案尚未完成，不能据本记录放行上线。

## 两遍分析的职责

第一遍使用纯文本缓存，保留全部命名主体、观点及十二类信息单元：功能、参数、价格、客户、场景、实施条件、案例、测评方法、风险限制、FAQ、比较和选择理由。信息单元带逐字 quote、Unicode 位置、主体、值/单位、限定条件和时间。未登记品牌和无命名主体的功能都保留；抽取内容只是“保存文字如此表述”，不是已批准事实。

限定条件为 null 时保留未知，不解释为没有限制；空数组表示没有抽到明确条件。字符串条件仅在可保留原值时转成单元素数组，并记录修复。任何条件、值、主体、时间不在本单元引文中，就保留拒绝记录，不借别处材料补全。结构失败、输出截断仍明确失败，不用空数组冒充成功。

第二遍通过 `ContextAnalysis` 保存问题、平台、采集条件、人工审核语境、材料版本 hash、模型策略及分段边界对应的解释。区分被比较方案、监测平台、参考来源、功能/品类、其他和未知。模型不接收自有/竞品身份写入权；身份确认和品牌库绑定仍由现有服务端审核决定。

同一篇来源正文对应不同回答/引用观察时，分别解释，保留 response/source ID。来源标题摘要仍保留第一遍信息单元，不把摘要解释成完整正文。自有材料的采集/批准与运行时版本冻结由 A03 接入；当前冻结已有批准事实及预留材料版本，原材料主张不注入回答分析输入。

## 证据和分数边界

- 原问题只有人工确认的逐字需求/约束才能成为 `requirement_id`；模型不能自行生成需求 ID。
- 主体必须恰好覆盖本段候选，不得用相同名称另一位置的引文替换；需求匹配必须同时指向本段单元和本问题原文。
- 第一遍的 `need_matched` 不直接生效。只有本回答、本主体单元与问题需求形成已校验匹配，且同单元没有明确反向匹配时，才可投影为需求匹配理由；仍标记模型解释未审核。
- 未登记的非方案主体保留在全部主体和信息单元中，不进入方案比较目标。角色未知保留候选和待核实状态。同一品牌在另一平台作为监测对象被提及，不能借其他平台的方案角色补出评分。
- 固定 30/30/20/20 规则不变，未知不补零、不重分权。材料未提供不等于产品能力缺失；来源观点不等于我方事实。

## 持久化、缓存与运行恢复

`ContextAnalysis` 复用已定义的新表，逐项保存 completed/failed/deferred、错误码、输入/语境/模型签名和用量。纯文本缓存签名单独计算，不含问题、业务 owner 或项目重要性；仍按项目隔离。语境缓存只在同项目、同文字与抽取结果、同问题/条件/材料版本和模型策略时复用。

只修改场景重要性不改变语境签名；新预算修订可直接复用抽取和语境结果，旧 Run 不变。请求前使用现有 context 配额预留；用量和结果在同一 fencing checkpoint 保存。未知消耗保留预留，不虚构为零；失败或额度不足明确保留未完成项。已保留的单元、提及不会因此删除。

为解决加入单元后输出膨胀，分段版本升级为 `unicode-nonoverlap-2-900`，每段至多 900 Unicode 字符，优先换行/句末切分，完整无重叠保留文字及尾部。每次仍限制输出，截断不自动补空或无限重试；较多片段的配额不足会逐项披露。

## 只读接口

- `GET /runs/{id}/information-units`：支持 owner 类型/ID、offset/limit，单页最多 100。
- `GET /runs/{id}/context-analyses`：返回本修订的语境状态、原问题/观察及解释，单页最多 100。
- Run summary/coverage 同时提供单元、条件未知数量、拒绝项与语境分层状态。页面接入后续遵循已确认的 v3 原型；本轮没有新增页面样式。

两接口沿用项目授权，只读不入队、不改写 Run。语义处理中保留原有权限/模型错误的安全诊断，不把密钥、请求头或提供商原始错误写入公开状态。
