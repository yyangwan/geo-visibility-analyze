# A05 从证据生成具体优化任务

本轮实现分析后端与只读接口，未调整页面样式、网关或生产环境。任务保存在既有 `PlatformDiagnosis`，通过现有行动入口转为计划，不建立平行建议系统。U02 的任务详情页面、E01 的行动修订与相关依赖审批、E02 的正式 Brief v3/ContentOS 创作仍分别待接入。

## 现在能形成什么任务

以下为虚构示例，说明规则的输出方式，不是客户真实审计结论。

| 输入观察 | 生成的具体工作 | 必须保留的边界 |
|---|---|---|
| 完整回答没有“云衡”，同时出现已核实或待核实的“锐川” | 围绕原问题准备“多门店权限适用说明与事实依据”，明确客户/场景、权限边界和证据清单 | 我方可以没有发现实体；未出现不等于产品能力缺失。未登记品牌身份未确认时先核实 |
| 总分未知，单项选择理由为我方 49、对比品牌 50 | 提供针对原问题的选型依据任务 | 不要求完整总分或至少十分差距；不把差距推断成检索原因 |
| 实际引用文章包含没有品牌名的“覆盖30家门店”案例及条件 | 准备我方案例材料，按客户类型、实施范围、时间、基线/结果、公开依据填写 | 该数据只属于观察原文；我方数字必须来自我方批准事实。没有授权或结果时保持待核实 |
| 检索候选正文包含相同案例 | 生成内容证据核查线索，保留检索候选身份 | 不写成“平台实际引用”，不据此推断渠道偏好 |
| 我方出现负面表述或回答与来源矛盾 | 生成具备双方原文的材料核查任务 | 模型情感/冲突不是客观真伪或事实审批，不自动生成对外纠错 |
| 同一问题下两个平台的单项表现不同 | 保留两边原文与采集条件，建立针对较弱观察侧的内容任务 | 单次跨平台差异不代表稳定偏好、因果或改进概率 |

## 六类机会与稳定目标

`opportunities.py` 直接消费 `brand_presence` 的稳定 `registry:* / entity:*` 目标、全部信息单元、问题上下文、原文核验及 A03 材料事实，不依赖旧竞争差距列表。

六类为场景覆盖、推荐竞争力、品牌认知、来源渠道、内容证据和平台差异。既有竞争对比图表的十分展示门槛不再限制本轮机会生成；旧 `competitive_diagnoses` 不再接入发布路径。运维性质的采集/身份等诊断仍保留。

场景缺席必须已有完整回答处理和明确身份；失败、未知、不完整回答不补零。单维比较只使用双方已知值。品牌定向问题单列不适用，不能进入中性竞争任务；合并任务时，不适用范围会进入 `excluded_scopes`，不会取消或混入其他有效目标。

没有总分或没有我方实体，不阻断成立的来源/单项任务。来源的没有品牌参数、价格、案例、测试、实施和限制等信息也能成为核查线索。只有与本问题上下文相连的单元才进入对应任务；没有需求匹配的来源信息明确标为相关性待核对。

## 任务包内容与证据权限

从第一次机会生成就输出严格 `TaskPack v2`：

- 稳定我方目标、资产键、事实改动键和执行意图。
- 具体交付物、资产名称、新交付或已有材料版本、参考 URL。
- 原始问题清单、问题 hash、逐平台/场景/指标子目标；不会拼接多个问题制造新 hash。
- 从已审核问题保留的目标客户，未知则明确 unknown。
- 具体章节与格式，例如参数表、报价边界、案例基线/结果、测试环境/样本、实施前置条件或限制清单。
- 渠道与理由、我方事实候选、缺料清单及验收条件。
- 同项目、同 Run 的真实原文引用，验证 owner、片段、全文 hash 和 Unicode code point 范围。来源正文还需 A04 的快照完整性与冻结版本证明。

观察事实、反向证据、假设、未知和我方材料状态分字段保存。竞品或无品牌原文只解释诊断，不转换为我方能力。来源渠道类目前输出我方资料准备与内容实验；引用文章只是线索，未自动承诺第三方投稿权限、渠道普遍偏好或收录保证。

## 材料就绪与合并

只有本 Run 冻结的当前有效我方事实，且原文和适用范围都包含本条完整需求短语，才列为主题事实候选；这是逐字主题关联，不等于语义上满足该需求。其他品牌、过期事实和未关联事实不会被填入 `own_fact_ids`。最终是否可写入内容仍需 E02 按作用域/身份/有效期复核。

只有一份已核实材料与所选主题事实明确相连时，定位它的具体版本准备更新；多份歧义或缺料时建立新交付物，保留材料待核实状态。材料未匹配不证明能力不存在。

`task_key` 使用项目、我方稳定目标、真实资产/交付目标、事实改动及意图，不含平台/问题。同一改动会合并各平台子目标、原问题、来源观察与反向证据。原文存在差异、条件或冲突的事实不会模糊归为一条改动；不做语义近似的自动合并。新子目标、材料/问题/提纲变化会改变任务签名，旧诊断不能被覆盖。

`actionability` 返回 ready_for_review、needs_material、needs_identity、insufficient_evidence 或 not_applicable。任务包的结构/容量约束失败会保留全部子范围和明确错误，不静默截断或开放行动入口。已有诊断再次持久化必须内容相同；行动创建校验任务键、项目、Run 和签名，计划保存同一任务包。

## 可解释排序与预算

排序绑定 `opportunity-priority-v1` 和项目业务偏好版本，依次看：纠错核查紧迫性、子目标中最高场景重要性、证据/材料准备度、目标覆盖、交付对象可控性及提纲步骤数。步骤数只是工作范围线索，不是工时估计。

场景未设置默认 50，并披露 neutral/custom；不输出 ROI、成功概率或四维权重修改。ready_for_review 与准备队列分开标识。

最多保留 1,000 个候选、200 个任务，按同一方向的规则保留高优先候选；较晚发现的紧急核查可以替换低优先候选。超出数、原文未处理、上下文不完整和未知品牌观察明确披露，未发现任务不等于没有机会。

新增 `GET /api/intelligence/runs/{run_id}/opportunities`，支持我方目标/平台过滤与分页（limit≤100）。默认返回冻结排序；显式 `priority=current` 只按当前业务偏好预览重排，披露这不是证据刷新及品牌配置是否变化。它不改旧 Run、任务包或签名，不创建采集/分析任务、不调用模型。公开报告继续使用冻结版本。
